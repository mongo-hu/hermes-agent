## 1. Hermes 的职责与改造范围

Hermes 负责决定“检查什么、需要算什么、结果是否符合要求”；OCCT Worker 负责识别结构和计算客观几何量。

| Hermes 负责 | 交给 Worker |
| --- | --- |
| 保存上传模型，关联聊天和 DFM 项目 | 加载 STEP，持有实际几何对象 |
| 查询 Feature → Check → Geometric 和规则 | 识别特征，保存内部部位和几何关联 |
| 确认材料、方向等必要输入，固定分析计划 | 按特征和 G ID 选择部位、执行算法 |
| 去重计算需求，管理进度、取消和恢复 | 复用模型与计算资源，逐 G 返回结果 |
| 执行规则，发布问题、定位和 HTML 报告 | 提供数值、测量点、面引用及采样数据 |

`occt.py` 与 `feature_recognition/occt_cpp.py` 现通过项目归属的常驻会话共用 Worker、模型快照和恢复记录；预览、识别、修订与测量不再各自启动短命分析进程。

开发阶段直接切换新契约，不增加旧协议适配器、字段别名或静默 fallback。不修改 Mold 数据库，不自动删除或转换已有项目和运行产物。

## 2. 共同契约与 Hermes 的使用方式

### 2.1 文档和接口如何维护

两仓库的文档按职责分别编写，不要求全文相同：

| 内容 | 维护位置 | Hermes 的要求 |
| --- | --- | --- |
| G ID 的工程含义、适用部位与取值方法 | 本体规则库 | 使用发布的权威 G ID，不另建 Worker 专用 ID |
| 方法、字段、状态和消息结构 | Worker 仓库 `docs/dfm-geometric-session-contract.md` 第 2 节 | 按同一约定构造请求、校验结果 |
| 可执行契约和联调样例 | Worker 仓库 `schemas/` 及契约测试样例统一维护并随版本发布 | 固定所接入的契约制品版本，运行消费端契约测试 |
| 客户端、计划、规则、Viewer 和报告接入 | 当前 Hermes 文档 | 由 Hermes 实现和验证 |

主契约为 `dfm.geometry/v2`。Worker 仓库发布的 `schemas/session-v2.schema.json` 是会话可执行契约的唯一来源，Hermes 固定并校验 `2.3.0` Schema bundle；双方确认公共接口变更后更新同一套定义和样例，不在 Hermes 手工维护另一套近似协议。

契约版本用于校验通信格式；引擎构建及依赖指纹用于追溯与缓存。不能只检查 EXE 版本号，也不能以两篇说明文档的内容哈希相同作为兼容证明。

### 2.2 Hermes 保留哪些标识

| 标识 | 在 Hermes 中的用途 |
| --- | --- |
| `project_id` / `run_id` | 项目与一次分析的记录，不作为 Worker 的计算对象编号 |
| `check_id` | 业务指标，如带孔 BOSS 柱“柱壁”；留在规则与问题处理层 |
| `snapshot_id` | Worker 返回的模型及特征状态编号，用于后续识别、修订和计算 |
| `feature_id` / `feature_kind` | 快照内的具体结构及其类别，例如 `BOSS_0007` / `hollow_boss` |
| `geometric_id` | 两端统一的技术指标 G ID |
| `forming_scope_id` | 快照内的运行时成型范围，如MAIN_POS或SIDE_01；不新增本体Region概念 |
| `context` | 该G实际需要的确认输入和算法参数；方向相关项可绑定forming_scope_id与显式用户方向 |
| `job_id` | Worker 一批几何计算的进度、查询和取消编号 |
| `evidence` | 数值的几何依据，包括面、测量点、局部采样数据和对应快照身份 |

普通计算不再使用 `worker_geometric_id`、`operation_id`、`calculator_id`、`metric_id/metric_ids`、`quantity_id` 路由，也不要求构造 Region 或 `face_indices`。传输层请求 ID 仍用于匹配应答，不再为每个 G 增加 `task_id`。

本体通用表中的 `concept_id` 仍保留，值为该技术指标的 G ID；Worker 的技术指标接口称为 `geometric_id`。规则包的 `properties_json`、`qualifiers_json`、`conditions_json`、`acceptance_criteria_json` 沿用数据库设计中的名称。

### 2.3 Hermes 何时调用各接口

| 方法 | 调用时机 | Hermes 保存或处理什么 |
| --- | --- | --- |
| `capabilities.get` | 连接建立后 | 契约版本、G/Feature、scope_modes、direction_modes、requires_complete_inventory与输入要求 |
| `snapshots.open` | 没有有效模型快照时 | 新 `snapshot_id`、导入诊断、预览与拓扑映射引用 |
| `features.discover` | 按feature_kinds与可选forming scope分批识别；长任务跟踪job_id | base/结果快照、实例、关联及coverage |
| `features.revise` | 用户修正特征部位时 | 新快照及修订记录，不覆盖旧 Run 使用的版本 |
| `forming_scopes.analyze` | 基于主/局部方向分析成型范围、可见性与倒扣候选；长任务返回job_id | base/结果快照、候选范围、覆盖和诊断 |
| `forming_scopes.revise` | 保存用户修订的范围、成型侧和局部方向，校验引用与一致性 | 新快照及修订后的成型范围 |
| `snapshots.merge` | 校验共同base、读依赖和写冲突后合并派生结果 | 新快照，冲突返回snapshot_conflict |
| `geometrics.compute` | 计划中仍有未取得的 G 结果 | Worker `job_id` 与本地 Run/JobManager 任务的关联 |
| `jobs.status` / `jobs.cancel` | 查询或取消几何计算批次 | 任务状态；取消不等于强制结束共享 Worker |
| `snapshots.renew` / `snapshots.close` | 使用期间续租、无使用者时释放 | 快照有效性和项目当前引用 |

## 3. 常驻客户端：把多次 EXE 调用改成持续连接

Hermes 管理 `dfm-geometry serve --stdio` 子进程，通过单行 JSON-RPC 2.0 通信。预览、Discovery 和正式计算共用连接，不各自创建短命分析进程。

RPC 即“远程过程调用”：Hermes 把方法名和参数交给另一个进程执行，再接收应答。这里的“远程”可以只是本机 C++ EXE，并不要求联网。例如 `snapshots.open` 是一次调用，提交 `features.discover`、查询 `jobs.status` 又是其它调用；一次业务识别轮次可以包含多次调用，不能把 RPC 次数、EXE 启动次数和识别轮次混为一谈。

客户端需实现：

1. 启动、能力握手和契约校验；缺少 v2 能力时明确报错。
2. 持续读取应答和任务事件，独立收集 stderr 日志；不得将日志当成协议数据。
3. 按请求 ID 分发应答，按 `job_id` 更新 JobManager 的状态和进度。
4. 几何计算期间仍能发送续租、查询和取消消息，不能让等待结果阻塞整个连接。
5. 连接中断或进程退出时，将所属运行句柄标为失效并通知相关任务。

多个项目不能共用一个无归属的“当前模型”变量。Hermes 保存项目、快照及所属 Worker 连接的关联；同一模型的计算由 Worker 排队，多进程调度时请求必须发往持有该快照的进程。

会话超时、内存预算和并发参数使用 `config.yaml`，状态与缓存遵守 Hermes profile 隔离。外部 C++ OCCT 与内部 PythonOCC 保持明确的后端选择，不因接口缺失而悄悄切换。

## 4. 两轮分组确认与增量快照

### 4.1 确认按范围解锁任务

用户上传模型后，加载/预览与主方向确认同时推进。第一轮业务识别以模型可用且主方向已确认为入口，覆盖全模型已接入的结构识别和主方向成型侧/倒扣候选分析；内部可按依赖拆批，但不是“主体壁第一轮、其它结构第二轮”。第二轮按已确认倒扣范围补识别和关联。结构算法本身可不使用方向，产品流程仍保证第一轮包含方向分析。外观面仅提出几何候选，由用户确认用途。

| 确认组 | 用户确认内容 | 解锁范围 |
| --- | --- | --- |
| 第一轮：主体壁与普通结构 | 主体壁、筋、凸台、带孔 BOSS 柱、孔及部位/关联 | 相关壁厚、尺寸、圆角、净距和关系指标 |
| 第一轮：产品与成型属性 | 外观范围/等级、型芯/型腔侧、边界及主方向约定 | 规则选择、相应主方向拔模和方向评价 |
| 第一轮：倒扣候选范围 | 各候选的范围，可拆分/合并，暂不必给出所有局部方向 | 局部结构关联与补识别，方向无关测量 |
| 第二轮：各局部组 | 局部退出方向、作用范围、区域内结构与参考主壁 | 该组的局部拔模与方向评价 |

每组独立提交，高置信对象可由用户批量确认，歧义项单独处理。确认 U01 不等待 U02；主体壁确认后不等待所有局部方向。未分类范围保留基础检查和覆盖记录。

局部结构确认和局部方向确认分别记录。目标部位已确认即可运行不依赖方向的G；候选未确认时只可做可丢弃的预计算，不发布正式合格结论。

Hermes 为确认组保存内部 `review_group_id`、目标对象/范围、所审内容指纹、用户来源、状态及时间。确认只对当时内容有效，相关部位或方向变化时重置受影响确认项；审核用途与清单完整性不能仅凭识别 confidence 自动通过。

### 4.2 识别结果与成型范围

Worker 分别保存几何 Feature、面级产品属性、运行时成型范围。`forming_scope_id` 只标识某快照内的方向作用域，不新增本体 Region 或业务 Check。

`features.discover` 按 `feature_kinds` 分批调用；局部请求通过 `context.forming_scope_id` 指定补识别范围。已识别的孔、筋、柱沿用实例编号，局部阶段只补关联或遗漏结构；目标范围外的主壁、支撑和遮挡仍需完整模型查询。

复用实例并增加范围关联是数据模型约束，不只是显示去重：同一 Boss 可部分参与 SIDE_01，也可与其它成型范围相交。`features`、面/边 `annotations`、`forming_scopes` 与 `relationships` 分开保存；完整/部分参与、实际部位与可空掩码由 Worker 第 2.13 节的记录约定表达，Hermes 不复制出“倒扣区 Boss”副本。确认组按实际参与对象和内容指纹绑定，范围变化时只失效相应关联与下游。

Hermes 读取 `coverage` 中的 `feature_kind/context/status/covered_geometry_ref/unresolved_geometry_ref/diagnostics`。状态为 `complete/partial/failed`，用于判断搜索是否完整；未完成筋清单不能让支撑数量返回 0，未完成邻域对象清单不能发布最终最近距离。complete 不等于识别已获用户确认。

局部方向和范围通过 `forming_scopes.revise` 写入新快照。向量采用模型坐标，表示成型部件相对塑件退出方向；Hermes 保存原输入及变换来源，不用柱轴或包围盒方向替代。主方向下的倒扣与局部退出评价分别保留。

### 4.3 派生快照合并与不可变批次

```text
snapshot_A0：同一个已加载模型
  ├─ 结构识别 → snapshot_A_structure
  └─ 主方向分析 → snapshot_A_direction
             ↓ snapshots.merge：共同 base、读依赖与写冲突校验
       snapshot_A1：结构 + 成型候选
             ↓ 分组修订/确认
       snapshot_A2：普通区域可计算，SIDE_01/SIDE_02 可分别推进
```

每个耗时写任务返回 `base_snapshot_id` 与结果 `snapshot_id`。Hermes 用 `snapshots.merge` 合并无冲突结果；`snapshot_conflict` 时保留两份产物并重跑相关分支，不用最后返回的快照覆盖项目当前状态。

输入副本、识别结果、审核修订、网格和计算产物保留不可变版本。快照中不同状态共享 LoadedModel；仅审核而未改变内容时可沿用快照，由 Hermes 保留确认记录。CAD 几何变化则重新登记模型。

### 4.4 聊天、续租与恢复

原始 STEP 保存到项目并记录哈希、单位和导入参数，不依赖聊天临时路径。Hermes 保存项目—Worker 连接—快照关联。用户审核、等待事实或计算期间续租；关闭聊天只释放对应引用，活动任务仍持有其所需快照。

快照过期或 Worker 重启后，重新打开输入，恢复并校验特征、属性、成型范围和用户方向，取得新句柄。旧面号不直接套用；无法验证的修订重新审核。磁盘 JSON 是恢复材料，不证明旧内存仍在。

## 5. 分阶段计划与任务依赖

### 5.1 一个分支就绪，就固定一个计划片段

Run 固定原始模型和本体规则发布版本，执行期间可以追加不可变的 `plan_fragments`。每个片段固定自己的几何/特征快照、已确认事实、适用规则、G/context、依赖指纹和能力版本；Worker 批次不接收计划片段 ID 或业务规则。

| Run 内记录 | 用途 |
| --- | --- |
| `plan_fragments` | 各已就绪分支的不可变计划；内部片段编号用于进度和追溯，不是每 G 的 task_id |
| 片段 `supersedes` 关联 | 修订后追加替代片段，旧片段和测量保持原状 |
| 结果有效性记录 | 当前结论仍有效或已 stale，保留失效原因与来源事件 |
| `result_manifest` | 生成某版报告时固定采用的片段、快照、结果绑定、规则、网格、证据和未完成项 |

新确认先追加片段，不修改已派发任务的输入。相关依赖改变时撤下过期结论、追加替代计划；原始结果和历史事件不改写。Run 封存后继续修改则新建 Run。规则发布版本变化进入新 Run，不能混入同一报告。

一个 Run 可引用多个来源快照；最终报告必须核验所有选中结果与最终确认状态一致。跨快照复用保留来源、建立已验证的新结果绑定，不把旧结果的 snapshot_id 改成最新值。

### 5.2 从 Check 生成计算需求

```text
某组 Feature、部位与必要属性确认
  → Feature → Check → USES_OPERAND
  → conditions_json 选择规则，补齐相关 Fact
  → acceptance_criteria_json 取得判定要求
  → 检查能力、确认、方向、对象清单等依赖
  → 固定就绪片段，合并同条件 G 需求并提交
```

柱壁检查的变量绑定不变：`boss_wall_thickness` 对应 `G_HOLLOW_BOSS_WALL_THK_MAX`，`adjacent_main_wall_thickness` 对应 `G_HOLLOW_BOSS_WALL_REF_THK`。两个厚度可各自计算，Check 等二者可用再判断；业务比值留在 Hermes。

Check实例同时绑定Feature、Check、适用成型context与规则版本，避免同一结构的主方向评价被局部结果覆盖。方向无关G可共用空context，但业务评价仍保留其实际适用范围。带孔 BOSS 柱优先使用具体子型规则，同一问题不重复报告普通BOSS结果。

同一 G、特征部位、参考对象和有效参数的请求只执行一次，可供多个 Check 使用。不同参考厚度 G 不因数值相同合并；G 的最大/最小口径不由 Check 临时改变。Operand 仍是变量绑定，不新增 CheckOperand 表。

### 5.3 确认、计算和覆盖三类状态

| 状态层 | 状态/含义 |
| --- | --- |
| Hermes 分组/任务 | `waiting_input/pending_review/ready/running/completed/needs_attention/stale/cancelled` |
| Worker 识别覆盖 | `complete/partial/failed`，另保留具体目标、有效范围和未处理范围 |
| Worker 逐 G 结果 | `ok/unsupported/not_applicable/missing_context/ambiguous_scope/failed` |

前置确认或计算缺失时任务不占执行线程，前置失败只阻塞其下游。Check 的可判定条件具备即执行，不等待整批指标和所有区域；规则组合求值按本体规则契约处理。

用户当前区域、确认后的必要补识别优先；其它已确认分支正常执行；精细场、全域加密及 HTML 使用后台预算。JobManager 同时映射本地片段与 Worker job，逻辑上独立推进不等于同时并发访问同一 OCCT 上下文。

## 6. 计算请求、局部方向与结果复用

### 6.1 指标按真实依赖解锁

| 指标 | 必须满足的前置条件 |
| --- | --- |
| 主体壁/柱壁/筋厚 | 目标部位、有效几何及必要配对确认；通常不依赖局部方向 |
| 孔深/孔径 | 孔子型、轴线、开口与终端定义明确 |
| 根部圆角 | 过渡面与根部归属明确；R/t 另等参考壁厚 |
| 支撑筋数量/连接 | 父柱和支撑关系明确，相关筋清单搜索完整且已确认 |
| 最近孔/筋距离 | 目标搜索域对象清单完整、有效配对明确 |
| 主方向拔模/倒扣 | 主方向与对应部位/成型侧明确；不等局部退出方向 |
| 局部拔模/方向评价 | 对应 forming scope、结构和用户局部方向确认，且 G 允许该模式 |

### 6.2 请求与 context

```json
{
  "snapshot_id": "snapshot_A2",
  "items": [
    {
      "feature_id": "BOSS_0007",
      "geometric_ids": [
        "G_HOLLOW_BOSS_WALL_THK_MAX",
        "G_HOLLOW_BOSS_WALL_REF_THK"
      ],
      "context": {}
    }
  ]
}
```

局部方向相关 G 使用以下 context：

```json
{
  "forming_scope_id": "SIDE_01",
  "draw_direction": [1, 0, 0],
  "coordinate_system": "model",
  "direction_source": "user_confirmed"
}
```

`forming_scope_id`、方向和作用面须与输入快照一致。严格限定主方向的 G 不可直接套局部方向；只有定义及 `scope_modes/direction_modes` 明确支持才派发分域请求。G 的有效 context 按声明归一化，不把主方向、材料等无关字段塞入所有厚度缓存键。

### 6.3 接收与复用结果

Hermes 按快照、Feature、G 和有效 context 关联结果，不依赖数组顺序。校验状态、类型、单位、几何身份、路径、清单大小与内容哈希；批次完成不等于所有 G 成功。非 ok 项保留 null 和原因，不填 0。

逐 G 的 `provenance` 记录 `source_snapshot_id/source_result_ref/dependency_fingerprint`。Hermes 直接复用已验证的同快照绑定；跨快照由 Worker 根据实际依赖生成新绑定并保留来源，不能仅因快照变化全量重算，也不能仅因 Feature 编号相同复用。

| 修改 | 保留 | 重新验证/执行 |
| --- | --- | --- |
| 主方向 | 方向无关结构、尺寸、厚度与 R | 主方向区域、相关成型归属、角度和倒扣及下游 |
| SIDE_01 局部方向 | 普通区域、SIDE_02、方向无关测量 | SIDE_01 的方向结果及受影响归属 |
| 外观/纹理标签 | 原始几何采样 | 相关规则、分区统计与判定 |
| 某柱部位或参考主壁 | 无关 Feature 和模型基础资源 | 该柱相关 G、配对和下游 |
| 业务阈值 | 定义与精度仍适用的客观量 | Evaluation、违规定位和报告 |
| 显示网格 | 仍有效的客观几何数据 | 投影、高亮和显示制品 |

超时、失败和取消不写成功缓存。重启后的磁盘恢复须核对引擎和依赖、特征状态与拓扑映射；缺少可验证依据时重算，不冒用旧快照。

## 7. 业务判定、问题定位和异步报告

### 7.1 将有效结果交给规则执行器

本节只规定接入行为；规则字段、OR-of-AND 三态求值和问题计数统一见[本地规则执行](dfm-rule-catalog-database-design.md#55-rule_version)。

每个 G 结果就绪后，更新依赖它的 Check；已有确定结论即可发布，不等待无关任务。保留数值、单位、来源与失败原因，不能把缺失结果填零，也不能从 Check 严重度推断 pass/fail。

例如柱壁最大厚度 2.1 mm、参考壁厚 3.0 mm，规则判比值时两项都是依据，最终形成一个柱壁业务结论。正文不另维护生产阈值或表达式副本。

### 7.2 定位先显示，报告后完成

相关Check可判定就发布结论；失败时立即发布Finding和已有范围，不等待所有组或整个Worker批次。修订使结论过期时发出stale更新并撤下当前统计，历史记录保留。只有部位范围时显示黄色“初步定位”；局部证据满足要求后更新为红色并提示“精确区域已更新”。颜色表示定位状态，不表示严重度。

本例分母为固定参考厚度，可将柱壁各采样厚度除以 3.0，定位比值超出要求的位置。参考主体壁不是违规柱壁，不能因参与公式就全部标红。两个变化场必须有明确位置配对；证据不足时保留初步范围。

每版报告固定result_manifest，核验选中结果与最终确认状态一致，保存采用的快照来源、规则、网格、证据和未完成组。Desktop按该清单查看相同版本；换网格重新映射，不复用旧三角形编号。

Agent整理内容，JobManager后台渲染HTML，定位完善与内容准备可并行。局部方向未齐时可生成阶段报告，明确列出待确认/未覆盖项；不能把已计算项均通过写成全部通过。已发报告绑定不可变清单，后续确认生成新报告版本，失败从原清单重试。

## 9. 会话数据与存放方式

采用“会话内存优先、制品文件共享、关键操作可恢复、结束后固定本地结果”的存放方案。当前实现使用 ManifestStore 的已提交内存状态、恢复日志和阶段检查点，小型 G/判定工作表走第 10.16 节的有界内存入口；不新增会话 SQLite 或 Redis。公共几何记录以 Worker 文档第 2.7、2.13 节为准；本节展开 Hermes 的消费和提交责任。向外部业务数据库归档仍是后续接入，不是当前已交付能力。

### 9.1 一个分析期间实际保存什么

预览资源按项目与模型输入持有；正式分析状态归属已有 `project_id + run_id`，不再增加一个同义业务会话 ID。聊天 ID、RPC 请求 ID、Worker 连接和 `snapshot_id` 分别承担交互、应答匹配、进程路由和几何状态引用，不能互换。Worker 连接归属仅是运行句柄，重启后重新建立。

```text
Hermes SessionState（按项目与 Run 隔离）
  inputs / import_parameters               原始文件引用、哈希和导入参数
  revision / current_snapshot_id           当前已提交的业务版本与几何快照
  geometry_projection                     与 Worker 同版本的几何记录投影
    features / annotations / forming_scopes / relationships / coverage
  facts / review_groups                    用户输入、确认指纹、来源与状态
  plans / active_plan_ref                  不可变计划及片段
  execution_records                        依赖、就绪/等待、job_id、进度与失败原因
  geometric_results / evaluations          G 结果绑定与确定性 Check 结论
  artifacts                                网格、场、证据及报告的稳定引用
  committed_sequence / checkpoint_sequence 日志提交与检查点边界
```

默认由 Hermes 进程内结构化对象和索引管理，不在每次查询时读取/重写整个项目 JSON。按 `feature_id`、类别、面/边、范围、关系端点、确认组和 G 依赖建立查询投影；反向索引从同版记录生成，不成为另一份可独立修改的数据。小型数值、列表、确认与任务记录在内存查询；大网格/数值场按需读取，不能全部复制到每个会话对象中。

几何字段由 Worker 校验和演化，Hermes 的用户确认、事实与计划由 Hermes 演化。通过接口交换小型记录、增量和内容指纹，引用共享目录中的不可变大制品；两进程不共享 C++ 指针。Worker 仅保存计算实际需要的状态，不装载企业规则和整个 Hermes 工作流。

### 9.2 成型范围字段如何消费

`forming_scopes` 是某快照内“作用范围与退出方向”的集合。SIDE_01 候选范围可以已知而方向未知，主范围与已确认的局部范围不能缺少有效方向。

| 字段 | Hermes 读取/更新规则 |
| --- | --- |
| `forming_scope_id` | 稳定的逻辑范围身份，例如 SIDE_01；不等于面号，也不自动代表实际滑块机构 |
| `mode` | `main` 为主方向，`local` 为局部退出作用范围；不代表局部坐标系 |
| `kind` | 范围类别：`main_forming`、`undercut` 或 `local_forming`；不从 SIDE_01 等编号推断类别，不等同于 mode |
| `geometry_refs` | 所属拓扑版本中的面引用，`kind: face, index: 101` 表示面 101，不是三角形 101 |
| `patch_mask_ref` | 只有部分曲面参与时使用几何/参数域掩码；缺少精确掩码时不假称精确分域 |
| `draw_direction` | 成型部件相对塑件退出的模型坐标向量；候选局部范围可为 null，表示未知而非零方向 |
| `coordinate_system` | 首版 `model`；用户输入其它坐标时先转换并保留来源 |
| `direction_source` | 已确认方向为 `user_confirmed`；未知方向为 null，不用算法轴线代替用户确认 |
| `status` | 候选、已确认或过期的几何绑定状态；单独的确认组记录仍保存于 Hermes |

例如 SIDE_01 包含面 101、`draw_direction: null`，意味着可以显示并确认该范围，但方向 G 暂不可执行。用户确认 `[1, 0, 0]` 后调用 `forming_scopes.revise` 得到新快照；不依赖该方向的尺寸/厚度按自身依赖判断。请求中的方向 context 从已提交范围生成并与快照校验，不能保留两份可任意冲突的方向值。

### 9.3 用户修订怎样进入可复用状态

1. UI 提交目标对象、修改内容及期望版本；仅备注等无关变化不使几何确认失效。
2. Hermes 在轻量日志中保存修订意图，释放持久化写锁后调用 Worker；确认指纹仅覆盖本组所审内容。
3. Worker 校验几何与关联，在同一原生模型上生成新快照，返回记录变化和实际影响；不覆盖已派发任务所读的旧快照。
4. Hermes 校验当前版本，提交新快照投影、相关确认和计划有效性，再应答“已保存”。冲突时保留意图与返回材料，合并或重新审核，不用最后返回结果覆盖当前状态。
5. 同时更新正向和反向查询索引；只有真实依赖变化的 G、Check 和定位退出当前有效集合。重试根据操作身份/内容实现幂等，RPC id 本身不提供业务去重保证。

没有几何内容变化的确认，可以只提交 Hermes 确认记录；Feature 部位、范围或参考配对改变必须经 Worker 校验。第二轮发现已有 BOSS_0007 参与 SIDE_01 时新增关系，而不是覆盖 Feature.kind 或创建另一个 Boss。只在对象实质拆分/合并时使用新身份并保留来源。

### 9.4 什么时候落盘，什么时候入库

“结束后统一入库”指完整记录归档到最终业务数据库，不是结束前没有任何恢复材料。默认恢复层沿用项目文件机制，不需要把业务数据库置于每次读写的热路径。

| 时机 | 必须保存/可合并内容 |
| --- | --- |
| 上传登记 | 原始文件、哈希及导入参数 |
| 用户输入、修订、确认应答前 | 可恢复的操作提交日志，不等分析结束 |
| 识别、修订或 G 批次完成 | 可恢复语义/结果检查点；保留版本、覆盖与制品引用，未检查点计算可重算 |
| 心跳、百分比、临时查询 | 主要保留内存，可节流合并，不要求每条 fsync 或写业务库 |
| 固定阶段/最终报告 | 先保证所选结果与证据可恢复，再提交不可变 result_manifest |
| 完成、取消或失败 | 归档输入引用、人工内容、有效结果、未完成项和终态；数据库暂不可用时保留恢复材料重试 |

日志采用单写者、提交序号、revision 与幂等操作记录；检查点采用原子发布，不覆盖尚被引用的版本。恢复先读取最近有效检查点，再核对后续已提交日志；Worker 重新打开模型并验证拓扑与修订后，取得新的运行句柄。执行中任务恢复为待核对/可重试，不能仅凭旧 running 状态继续声称正在计算。

日志、检查点和大制品位于项目内；检查点必须包含恢复所需的小型状态或已经持久化的引用，不能指向唯一存在于旧进程内存的对象。完成归档按 Run/提交版本幂等；失败只重试归档，不重新计算仍有效 G。不得在归档完成前删除唯一恢复副本。

### 9.5 Redis 是可选存放方式，不是另一套数据模型

先实现本地内存和恢复日志即可。需要跨 Hermes 进程共享时，可将同一逻辑记录按 profile/项目/Run 分区放入 Redis，仍通过统一状态访问入口、revision 和幂等提交更新；不要同时维护两份可独立写入的内存/Redis 主状态，也不要求 C++ 算法直接访问 Redis。

Redis 不保存可供另一进程直接执行的 OCCT 指针，不反复搬运大网格和数值场。活动会话要有明确的续期和淘汰边界；仅内存写入成功不等于用户修改已可靠保存。需配置并验证持久化/恢复保证，不能将 AOF 每秒同步等同零丢失；本地轻量提交日志可继续承担已确认用户操作的恢复底线。

计划是固定输入的工单，执行记录是实时进度，队列只装就绪任务引用。Redis 即使承接队列，也不能替代依赖判断、Worker 模型归属路由或执行幂等。不存在可执行任务时持久保存等待状态，不占用计算线程；更换队列实现不能改变 Feature/G 数据含义。

新增验收需覆盖：用户确认应答后异常退出可恢复；第二轮结构不重复且多范围关联可查询；小型状态走内存而非逐次全量文件读写；归档失败可独立重试；每个报告引用都能定位到已提交的制品。模拟算法与规则只用于验证这些框架性质，明确 fixture 来源，不宣称工程检测通过。

## 10. 本轮实施边界与验证清单

### 10.1 固定的存放方案

当前本地 Desktop 只保留一套运行状态入口：Hermes 进程内按项目缓存已提交状态及索引，Worker 进程内保存原生模型和不可变几何快照。项目文件负责恢复和最终本地归档，现有只读 SQLite 只查询已发布本体规则；不新增会话 SQLite，不引入 Redis，也不把同步远程业务数据库作为几何计算的前置条件。未来业务数据库归档是已有结果的消费者，不重新决定测量或规则结论。

几何修订必须提交 Worker 后再更新 Hermes 投影：`features.revise` 处理结构/部位与必要关联，`forming_scopes.revise` 处理范围和方向；仅审核且内容未变化可只保存 Hermes 确认记录。Worker 返回的 annotations、relationships 同样参与恢复指纹，不能只恢复 features 而丢失多属性或范围关系。

### 10.2 记录与推进约束

- `forming_scopes.kind` 描述范围类别，`mode` 描述主/局部方向角色；外观和定/动模属性放在 annotations。同面允许多个不同维度的属性，不把它们编码成 Feature.kind。
- 第一轮在主方向确认后识别所有已接入结构并分析主方向范围；内部批次数不决定业务轮次。确认倒扣范围后第二轮复用已有 Feature 身份，补关系或确实遗漏的对象。
- Check→G 依赖从规则包取得；G 的 context/方向/完整清单依赖从 Worker 能力取得；本次等待原因固定到计划片段。Worker 内部算法依赖不变成 Hermes 的另一套路由 ID。
- 确认组的所审内容独立指纹化，局部缺方向只等待对应任务。工作流负责自动重新检查依赖，不依赖大模型猜测 next_action。
- 已派发计划不可变，运行进度单独更新；修订追加替代片段。每项有效结果可推动对应 Check，证据和 HTML 后续完善，最终清单固定来源和网格身份。

### 10.3 必须用实测证明的完成条件

| 项目 | 证明 |
| --- | --- |
| 内存状态与恢复 | 重复查询不反复解析完整清单；跨实例版本校验正确；强制中断后已应答的人工修订可恢复 |
| 原生资源复用 | 同一源码构建的真实 Worker 在预览、两轮识别、修订与多批 G 中只导入一次 STEP；重启的恢复导入单独计数 |
| 数据模型 | 快照保留 features、annotations、forming_scopes、relationships、coverage；局部关联不复制 Boss，同面多维属性可查询 |

### 10.5 项目状态提交与阶段检查点

`ManifestStore` 是项目状态唯一读写入口。`project_manifest.json` 作为阶段检查点，`recovery/manifest.events.jsonl` 保存检查点之后的增量提交；调用方不能直接读取检查点来判断当前确认、计划或运行状态。

每次提交在项目进程锁内读取当前 revision、检查相应版本条件、生成增量、追加带校验和的日志并 flush/fsync，成功后才发布内存版本及应答。数组记录按各自实例 ID 更新；运行进度变化不重复写入未变化的 Feature、Plan 或网格。检查点达到内部批次/大小预算时压缩，也可在阶段结束时显式刷新；压缩失败不撤销已经可靠提交的事件。

读取优先使用进程内已提交状态，并同时检测检查点与日志签名以发现另一进程的提交。冷启动读取检查点后按 revision 连续重放日志。仅最后一条未完整写入的事件可忽略并在下次提交前截除；完整事件的校验和错误、版本断裂或项目不匹配必须报错，不能悄悄恢复成旧的成功状态。

用户确认、输入和几何修订是关键提交，不等正常分析结束才保存；高频进度可以在通知层合并。结束后固定结果清单及阶段检查点。日志不是新的业务数据库，也不要求 Worker 直接读取；Worker 仍通过会话接口接收几何修订并返回权威语义状态。

### 10.6 独立确认与 Desktop 接入

普通结构以 Feature 实例建立确认记录，Desktop 按类别折叠展示并支持选组批量确认；展示分组不等于把所有结构合成一个不可拆的确认门槛。指纹只包含结构、部位、参数及参考关联，不包含 Worker 句柄、进度、时间和确认状态本身。局部补识别仅新增范围关联时，普通结构的原确认不失效。

主成型组确认必须同时把方向与作用范围提交给 Worker，不能只修改 Hermes 确认状态。倒扣范围确认后触发局部补识别；局部结构和局部方向分别确认。Desktop 从当前项目读取组状态、目标几何和阻塞原因，提交时携带 revision；不能直接修改共享缓存或依据旧界面面号自行重建几何结果。

某组确认完成后可以创建包含 ready、pending_review、waiting_input 的阶段计划；未确认的其他组不应成为全局禁行开关。缺失业务事实的 Check 保留待办身份，不得把“还不能选择规则”报告成不适用或全部通过。

### 10.7 等待不等于完成

执行器每完成一批就提交原始制品引用、已执行片段 ID 和可确定的规则结论，立即发布问题及初步定位。还有待审核或缺输入片段时，Run 保持 running，stage 为 waiting_review 或 waiting_input；执行线程退出等待，不轮询、不占用计算槽，也不生成最终报告。缺少规则适用事实的检查以 pending_inputs 保留到计划，不能丢成“不适用”。

pending_inputs 保留 clarification_id、fact_name、check_id、feature_id 及问题内容；completed_fragment_refs 放在 Run 执行记录，不能通过修改旧 Plan 片段来记录完成。自动推进只操作当前 JobManager 拥有的 Run，不接管其它 Hermes 进程的任务。

审核或输入改变后生成替代计划片段；追加操作保留旧片段内容，通过 supersedes 指出替代关系。JobManager 按持久化的 completed_fragment_refs 排除已执行片段，并唤醒等待中的 Run。追加与执行退出之间的竞态必须通过同一调度锁处理，不能丢失唤醒或启动两条执行线程。没有未完成依赖且当前就绪片段都已执行后，才能封版、生成最终结果清单并交给异步 HTML 流程。

局部结构确认指纹只包含范围几何、参与关联和结构内容；变更局部方向不撤销未改变的结构确认。用于规划的范围必须来自所固定 DiscoverySnapshot 的 forming_scopes，不能通过 Worker ID 前缀猜测同一会话。

### 10.9 人工几何修改的提交与范围编辑

用户提交修改时必须提供读取时的项目 revision。服务先校验并把操作意图写入项目恢复日志，再调用 Worker 生成候选新快照。准备阶段不把该快照切为当前状态；提交时校验模型输入、主方向和几何快照头仍与起点一致，原子保存实际语义投影、审核状态、失效范围及操作终态。心跳、百分比和其它非几何更新不构成几何冲突。发生几何冲突时明确拒绝，不用最后返回结果覆盖较新状态；未提交分支不用于正常计算。

恢复日志中的 geometry_edits 是内部操作记录，不是对外 G task_id：保存 edit_id、输入哈希、基快照、方法/参数、pending/committed/failed 状态及结果快照引用。Worker 自身的恢复步骤可以先登记准备完成的分支，但 current_snapshot_id 只在采用后推进。恢复时以 Hermes 已提交的快照头选择几何状态，不采用最后一个返回的未提交分支。

`update_forming_scope_geometry` 修改一个现有局部范围的面选择，范围保持 candidate，未知方向仍为 null；不能借编辑范围自动确认局部方向。Worker 保留旧快照，并重建/清理受影响的范围成员关联和覆盖状态。Hermes 使该范围的倒扣范围、局部结构及方向确认重新待审，保留未改变的普通结构确认；其它范围和方向无关 G 不受影响。重新确认范围后才补识别与审核局部结构。

拆分/合并通过同一 `forming_scopes.revise` 请求显式传入新范围及 retire_scope_ids，旧范围标为 stale，保留来源；新范围重新审核。不能用字段缺失表示删除，也不能让 stale 范围继续进入就绪/等待任务。`snapshots.get` 只读取某版语义状态，不导入模型，也不移动当前快照头。

### 10.10 Feature 修改与等待期间的显示一致性

Feature 的选面修改同样必须重建其与现有成型范围的成员关联；无交集的旧关系移出当前快照，相关局部识别覆盖改为 partial。Hermes 根据返回的实际结构内容和成员关系重建受影响的局部结构审核组，不能只把旧组标为 stale 而留下不可确认的空缺。方向未变化时保留独立的方向确认；普通结构只重审实际变化的 Feature。

替代计划即使没有新增可计算 G，也必须立即重算当前有效规则结论并刷新 Viewer。等待用户重审不表示旧结论仍有效；历史数值和制品保留用于追溯，当前问题与高亮只采用新计划仍然选择的结果。快照租约到期按会话恢复流程处理，不要求用户重新上传，也不把未提交分支恢复成当前状态。

### 10.11 参考对象依赖的确定性编排

Schema bundle 2.2.0 的 G 能力新增必填 requires_relationships，元素为 type 和 target_feature_kind；空数组表示不依赖参考对象。Hermes 不根据 G 名称猜依赖，也不自行选择参考面，而是解析当前 DiscoverySnapshot 的 relationships。例如 Boss 参考主体壁厚要求 adjacent_main_wall 关系指向 main_wall。

计划逐 G 校验关系唯一性、目标类别和目标结构确认。缺失/歧义保留带关系类型和候选对象的阻塞原因；参考对象未确认时，仅等待使用它的 G。其普通结构确认组、实际关系和参考几何内容进入片段依赖，不能只固定 Boss 自身的确认引用。参考主体壁可位于 SIDE_01 之外；不因此要求它成为该局部范围的成员。

柱壁自身厚度可先执行，参考厚度等待对应主体壁确认，Check 在操作数齐备后判定。参考对象变化后追加替代片段，旧结果保留来源；自身厚度的物理计算缓存仍可复用。业务 Check→G 来自规则库，G→参考关系来自 Capability，本次目标与确认状态来自快照和 Hermes 审核记录，三者不能混在硬编码的阈值判断里。

片段以 Feature + G + 有效 context 为最小依赖单位，不把依赖不同的多个 G 因为当前状态相同就合成一个审核门槛。相同需求的多个 Check 共用该片段。用户界面可继续按结构/范围分组，Worker 计算请求也可批量组织；展示分组、依赖片段和传输批次不是同一概念。追加计划时只替代对应 G 的片段，避免一个就绪片段只替代了旧等待片段，却遗留重复的有效计算结果。

Finding 保存实际采用结果的 plan_fragment_refs。参考对象修订时按这些来源片段的 reference_dependencies 判断影响，不能因为历史 Plan 曾引用某片主体壁，就撤销当前已改用其它主体壁的结论。关系的来源、置信度等审计属性不进入普通结构确认指纹；关联目标和实际参考选面仍参与确认。

### 10.12 产品/成型属性的独立审核

2.3.0 的 annotations 使用 Worker 第 8.7 节记录格式。Hermes 为每个有效 Annotation 建立 surface_attribute 审核组，按 kind 折叠展示，所审内容为类别、值、实际几何引用和 properties。来源、置信度、时间及快照句柄不改变审核指纹；实际内容变化只重审对应属性。已退役记录不再生成待办。

用户确认原内容时，只提交 Hermes 审核记录；修改类别值或选面/选边时，先通过 annotations.revise 提交 Worker，再原子保存返回投影和新审核组。该动作沿用几何修改意图日志、版本冲突和恢复保证。HTTP 与 Agent 使用 revise_annotations，包含 expected_revision、annotations、retire_annotation_ids；Worker 仍持有唯一几何权威状态。

同一张面可以分别确认外观、定/动模及型腔/型芯侧属性，不将这些状态塞进 Feature.kind。分型边界保存 edge 引用；初版 Viewer 可以用相邻面作粗定位，必须标明是关联面而不是精确边线。面属性可在 Viewer 中修改值和选面；边界的边引用通过契约/API 修订，边选择交互与精确曲线制品后续完善。

属性审核不自动伪造规则 Factor；只有明确的本体映射才可把属性转换成业务事实。当前 G 不读取这些属性，因此属性修改不派发一轮无关几何计算；相关规则输入仍按已有缺失事实流程确认。属性自动识别属于后续算法覆盖，本轮用明确标识的候选数据验证接收、修订、审核、重启恢复和复用。

实施记录（2026-10-28，2.3.0）：已接通 revise_annotations、HTTP PATCH discovery/annotations、修改意图提交、独立 surface_attribute 审核及面/边修订恢复。review_context 从已保存的能力元数据读取 annotation_kinds，不为读取审核界面启动识别。Desktop 支持新增面属性、改值和选面；分型边界明确显示关联面粗定位。属性确认不会误确认同名 Feature，也不会触发当前无关 G 的重新计划。

### 10.13 依赖片段与计算批次分开

计划片段仍以 Feature/G/context 为最小依赖单位，不因批量调用而合并审核、失效或完成身份。Hermes 从当前就绪且未执行的片段中选择传输批次，只合并同一逻辑快照和同一能力版本的请求；相同 Feature/context 合并 geometric_ids，同一 G 只发送一次。返回结果按 Feature/G/context 找回所有来源片段，分别保留 plan_fragment_ref，不在公共协议中增加 task_id 或 Check 路由。

首批优先选择不再依赖审核/输入的 Check，先计算它尚缺的 G，例如 Boss 柱壁检查的柱壁厚度与参考主体壁厚度。后续优先同一 Check、同一 Feature，再填充其他就绪项；内部软预算为每批 8 个不同 G 请求。单个已有片段若超过预算则独占一批，不拆分其完成身份。不同快照、不同能力版本、待审核或缺输入的片段绝不夹带进请求。

JobManager 每批结束后重新读取当前计划和 Feature，校验并提交结果、已完成片段及可确定的问题和 Viewer，再选择下一批。批次执行期间新增计划不丢失；被替代片段的返回值可保留追溯，但不得重新发布为当前结论。取消、批次失败或结果缺项时，不把本批片段登记为完成。之前成功提交的批次不因后续失败而丢失。

增量结果文件按批次唯一命名，kind=geometric_batch，仅保存本批结果而不是反复复制全部历史结果；发布后不覆盖。本次 Run 的 geometric_results 工作表按片段/Feature/G/context 更新并原子替换，重试不能重复累计同一结果。每批返回后由 JobManager 对累计工作表执行规则和发布 Viewer，不把单批增量误当作完整结果。Viewer 将已就绪但尚未执行的片段也列为未完成，不能在首批之后提前显示分析完成。

仅传输编排改变，沿用 2.3.0 契约，不新增配置项或 Worker 算法概念。接入验证需证明批量请求实际发生、来源不串线、首批 Viewer 先于后续计算和 HTML、并且失败/取消保留已提交批次。批量 RPC 减少不等同于大型模型整体性能已经验证；共享网格的重复解析和文件校验见第 10.14 节。

实施记录（2026-10-28）：runtime/geometric_batches.py 是 JobManager 与 OCCT 适配器共同使用的批次选择入口。JobManager 只执行本批选中的片段，完成后按最新计划发布并继续调度；Adapter 将返回结果绑定到全部来源片段，零新增 G 的共享消费者可同批处理。计算过程中更新计划不会因执行器仍持有旧 Plan 而按旧计划重新生成当前结论。收到取消后不提交新批次的完成状态。

验证：最终 DFM/审核路由回归为 55 个 Python 文件、481 项通过，2 项旧可选环境用例跳过。真实 Boss 用例覆盖两 G 合并、首批问题/部分完成 Viewer 先于第二次 RPC、局部依赖后续确认续算、下一批异常、取消及缺项不确认完成。原生适配器用例证明相同 G 一次计算可形成不同片段的结果绑定，重复调用不累计重复记录且旧增量文件内容不变。公共会话/文档契约 9 项、解析几何消费端联调 5 项通过。尚未证明大型模型全链路性能或完整 Desktop 安装包验收。

### 10.14 共享几何制品的元数据复用

预览、识别和小批次计算引用同一份 preflight、render_scene 和 topology_map 文件。Hermes 缓存这些文件的 SHA-256、大小及少量快照元数据；不缓存第二份 primitives、faces、edges 或完整 JSON 树。绝对文件路径、文件身份、大小及纳秒时间组成缓存签名，签名变化后重新读取。缓存有数量上限，返回副本，不能让调用方修改缓存内容；不同项目不按文件名复用。

批次期间可复用未变化制品的已验证摘要，Viewer 只取 scene/topology 的快照头，不为两个编号反复解析大型网格。最终封版前对共享文件强制重新计算完整 SHA-256，并与已登记制品描述比较，随后继续既有几何证据内容校验。文件修改、替换、读取期间变化或摘要不符不能靠旧缓存放行；签名缓存不是最终内容证明，也不缓存运行中的结果表、用户确认或规则结论。

本优化仅在 Hermes 进程中保存小型元数据，不引入 Redis、会话 SQLite 或新公共 RPC 字段。性能验证需要记录真实文件读取/JSON 解析次数，覆盖重复调用、文件变化、缓存回收、副本隔离及强制内容校验；不能只看总测试数量或仅用计时宣称所有大型模型已经达标。

共享制品不为每个 Run 再复制一份。Viewer 的 scene_path、topology_path 等路径相对于 Viewer 清单自身所在目录，不能只取原始文件名；引用跨项目子目录时仍须解析到同一项目内部的真实文件。预览、识别和分析三个 Viewer 入口采用同一规则，测试必须实际读取引用目标并核对网格/拓扑身份，不能只断言清单文件存在。

实施记录（2026-10-28）：geometry/artifact_metadata.py 提供有界 LRU，最多保存 64 个文件、每个文件最多 64 KiB 的小型摘要信息。预览、识别、批次校验和 Viewer 共用该入口；运行结果表和人工状态不进入此缓存。Windows 路径 stat 与句柄 fstat 的时间语义不同，因此句柄检查使用文件身份、大小和修改时间，路径自身的完整签名另外作读前/读后检查。

验证：56 个 DFM/审核路由 Python 文件共 492 项通过，2 项旧可选环境用例跳过。真实 Boss 分析证明未变化的 render_scene、topology_map 各解析一次，预览、识别、首批分析 Viewer 的引用目标均可实际读取且快照身份一致；最终封版拒绝缓存签名未变但内容被修改的共享文件。Desktop 6 个文件、25 项交互测试及正式 build 通过。构建包含未提交工作区源码，不能当作可追溯的正式安装包发布。

### 10.15 真实 Electron 三维验收

Viewer 清单携带所属 project_id。嵌入视图优先使用调用方的项目身份，独立弹窗从清单恢复；两者同时提供但不一致时拒绝加载，不能把 A 项目的几何修订发到 B 项目。弹出窗口保留原有分组确认和人工修订入口，仍通过 Hermes API 提交，不直接修改 Worker 或磁盘 JSON。

审核提交同时携带读取时的 revision 和 expected_snapshot_id；后者使用 review_context 已返回的 Hermes snapshot_id，不是新的一套任务或算法 ID。进度、Run 状态和制品登记可以推进项目 revision，但不能改变所审几何快照。快照仍一致时，按内容比较后提交，并保留期间的运行结果；快照或确认组内容变化则明确冲突。人工修订准备与提交两次校验几何身份，不能把允许无关进度更新解释成允许覆盖并发几何修改。

### 10.16 小型 G 结果与判定工作表的内存复用

runtime/result_documents.py 统一管理 geometric_results 和 evaluations 两类小型工作表。写入者原子落盘并预热结构化内存投影；规则、定位、Viewer 和报告读取者复用该投影，不在每个阶段重新读取和解析同一 JSON。缓存按绝对路径和文件版本隔离，返回独立副本；外部修改或原子替换使旧缓存失效，摘要不匹配不能继续使用旧数据。

缓存只保存小型结构化结果，不装载 scalar_field、render_scene 或 topology_map；最多 32 份文档，单份编码体积 4 MiB、总编码体积 16 MiB，Python 对象开销另计。超过预算照常使用磁盘，不删减记录。阶段制品仍原子写入并 flush/fsync 用于恢复/追溯，最终封版强制读取实际 G 文件并核对摘要；内存命中不是跳过最终校验的理由。累计表可更新，已发布 geometric_batch 和最终结果清单保持不可变。本项不新增 Redis、会话 SQLite 或公共 Worker 字段。
